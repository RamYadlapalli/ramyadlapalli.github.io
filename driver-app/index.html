Designing an offline first driver app for drivers who lose signal

Ram Yadlapalli · November 2026

Before we wrote the driver app, I spent 3 weeks riding along with pickup and delivery drivers. Most of how the app behaves offline comes from what I saw on those trips.

A driver's day starts at the terminal and then goes out to customer docks and stops along the route, some of them rural. The signal comes and goes all day. When it drops, the driver still has to arrive, pick up freight, take photos and close out the stop, and nobody wants to stand at a dock waiting for a screen to load.

So the app records actions on the phone first. When a driver taps arrive or complete, the local state changes right away and the event goes into an outbox saved on the device, which survives the app being closed or the phone restarting. Most actions work this way with no signal. A few screens that need fresh data from the server wait until the phone is back online.

Order matters as much as delivery. If a completion reaches the server before the arrival at that stop, planners see the wrong picture. The outbox sends one event at a time, oldest first. It pauses while the phone is offline and retries failed sends with backoff.

How a driver action travels from the phone to the server, and how dispatch changes come back.

On the server

Events arrive in Azure Event Hubs, which carries location traffic too. At a single carrier that comes to about 500K driver events and about 1.5M GPS pings on a typical weekday. GPS pings are sent only while the phone is online.

From there, driver events go to Service Bus with one session per driver. That keeps each driver's events in order, while different drivers are processed in parallel. Every event carries an ID created on the phone, and because a retry can deliver the same event twice, the server checks that ID so a duplicate is not applied again. Photos get similar care: the app uploads them to Blob Storage first and sends the event only after the uploads succeed.

When the route changes

Dispatchers change routes during the day, sometimes while a driver is out of coverage. If a late event arrives for a stop that has since been removed or completed, server rules check it against the current route, and the current state wins. Changes also flow the other way. A push notification tells the app that dispatch data has changed, and the app fetches it and merges it with what the driver has already done, so a refresh doesn't wipe out work in progress.

I also built the native modules that give the app its maps and navigation. Later features such as Delays and Breaks and Customer Ratings were built into this same app.
