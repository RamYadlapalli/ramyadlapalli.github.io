Designing an offline first driver app for drivers who lose signal

Ram Yadlapalli · Case study · Engineering

Pickup and delivery drivers work in dock yards and on rural roads where the signal comes and goes. I designed our React Native driver app so drivers never wait on the network and their events reach the server in the order they happened, each counted once.

At a glance

  • My role: key architect and lead developer of the driver app, including the native modules for maps and navigation
  • Volume at a single carrier: about 500K driver events and about 1.5M GPS pings each weekday
  • Stack: React Native with native modules, Azure Event Hubs, Service Bus sessions, Blob Storage, push notifications

The problem

Before writing any code I spent 3 weeks on the road with drivers to understand a day in their life. The design came from two facts of the job. First, the signal drops all the time, and a driver will not stand at a dock waiting for a spinner. Second, the order of events matters. If a delivery arrives at the server before the arrival at the stop, planners see the wrong picture and the data is wrong.

The constraints

  • Drivers have to keep recording their work offline, and the app has to catch up when the phone reconnects.
  • Events for one driver must be processed in the order the driver did them.
  • Phones retry, so the same event can arrive twice. It must only count once.
  • Dispatchers change routes while drivers are offline, so the app must merge server changes with what the driver has done locally.
  • Volume is real: about 500K driver events plus about 1.5M GPS pings each weekday at a single carrier.

The design decisions

Every action is applied on the phone first, then delivered through an ordered, idempotent pipeline.

  • Native modules for maps and navigation. I built the native modules that give the React Native app its maps and navigation.
  • Local first. Every action updates local state immediately, so the screen never waits on the network.
  • Persisted outbox. Each driver action is written to a queue on the phone that survives app restarts, pauses while the phone is offline, and retries with backoff.
  • One at a time per driver. The outbox sends a driver's events serially, oldest first, to Event Hubs, which carries both driver events and location traffic.
  • Ordered end to end. On the server, Service Bus sessions keyed by driver keep each driver's events first in, first out, while different drivers are processed in parallel.
  • Idempotent. The phone generates an ID for each event, and the server ignores any ID it has already processed. Retries are safe.
  • Late events. When an old event shows up after a dispatcher has changed the route, server rules check it against the current route, and the current state wins.
  • Photos first. Images go to Blob Storage before the event that references them is sent, so the server never sees an event pointing at a missing photo.
  • Merging changes. When dispatchers change something, a push notification tells the app to refresh, and the app merges the server data with the local state instead of overwriting the driver's work.

The result

Drivers keep recording stops, pickups, and exceptions with no signal, and when the phone reconnects their events reach the server in the order they happened, each counted once. Event Hubs carries about 500K driver events and about 1.5M GPS pings each weekday at a single carrier.
