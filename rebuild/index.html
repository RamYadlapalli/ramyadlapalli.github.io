Moving a live logistics platform from an on premises monolith to Azure

Ram Yadlapalli · Case study · Engineering

In 2018 I led the rebuild of our first and final mile platform for LTL carriers. It moved from an on premises ASP.NET monolith to event driven services on Azure and Kubernetes, and the carriers on it kept running the whole time.

At a glance

  • My role: key architect and lead developer across the web app, the backend, and the driver app
  • Stack: React and TypeScript, Node.js, C# and .NET, React Native, Azure, AKS, Azure SQL
  • Today: 11 LTL carriers in the US and Canada, about 20,000 drivers, roughly 1M transactions an hour, 99.7% uptime

The problem

I was one of the first two engineers, and in 2017 we built the MVP as a single ASP.NET application running on premises. That was the right call for an MVP. Once real carriers were on it, though, we could see how it was actually used. Different parts of the system had very different load and change rates, and they were all inside one deployable unit on premises.

The constraints

  • Carriers were live. Drivers were running routes every day, so there was no window to stop and switch over.
  • The platform is multi tenant, so every change had to keep each carrier's data separate.

The design decisions

We did not split the system on day one by drawing boxes on a whiteboard. We split it where real usage told us to. As we got more clarity and first hand experience, each piece that needed to scale or change on its own became its own service.

Before and after the rebuild. The optimization engine is owned by the operations research team; I designed the services and integrations around it.

  • Move to Azure. We left the on premises servers and moved to Azure, with services running on Kubernetes (AKS) and data in Azure SQL.
  • Node.js and TypeScript services. New services were written in Node.js and TypeScript, with C# and .NET where it fit better. I was the lead developer on the backend and on the React web app for planners and dispatchers.
  • Messaging between services. Where work can be queued, services hand it to each other through AMQP messaging and Azure Service Bus, so they can scale on their own.
  • Event Hubs for driver and location traffic. Driver events and GPS pings are the highest volume streams, so they come in through Event Hubs.
  • Other Azure components. SignalR and the other pieces came in the same way, when real usage showed we needed them.
  • Blob and File Storage. Photos, documents, and integration files live in storage built for them, not in the database.

The result

Carriers stayed live through the whole rebuild. The same architecture now runs 11 LTL carriers in the US and Canada, about 20,000 drivers and 1,000 planners and dispatchers, at roughly a million transactions an hour and 99.7% uptime. It also let us move to monthly releases in 2022.

I still revisit it. Cloud cost is something I look at all the time, and I keep asking the same question about each component: if I built this again today, what would I change? Then we refactor when the answer is worth it.
